## 1. What the UI is actually telling you

This banner is generated by `worker/src/syncPosture.js:70`, which catches three
LinkedIn-flagged states on the Connections surface:

| Signal in the error | What LinkedIn did | Posture |
|---|---|---|
| `ERR_TOO_MANY_REDIRECTS` | Bounced the browser between `/authwall` ↔ `/login` ↔ original URL | `blocked` |
| URL contained `/authwall` | Forced the session to log out | `blocked` |
| URL contained `/checkpoint` or `/challenge` | Demanded a security verification | `checkpoint` |

The current code maps all three to a **2880-minute (48 h) backoff** and surfaces
"Reconnect required" in the UI. The "Next attempt just now" timestamp means the
worker last *attempted* a sync just now and got immediately blocked again — the
cooldown counter resets each attempt.

**This is the symptom of one root cause:** the worker is egressing directly from
the DigitalOcean datacenter IP `167.71.211.25`, and LinkedIn has that ASN on
its known-bot list. Every retry from the same IP returns the same redirect.

## 2. Two failure modes you can be in (and how they look the same on the UI)

| Mode | What's true | What "Reconnect" alone will/won't do |
|---|---|---|
| **A. Session is stale / cookies expired** | LinkedIn rotated `JSESSIONID`/`lidc`; the stored set no longer authenticates. | Reconnect via noVNC works — get fresh cookies, posture clears, syncing resumes. |
| **B. IP / account is flagged** | LinkedIn has marked this combo as a bot. Cookies are fine; LinkedIn refuses regardless. | Reconnect from the **same** datacenter IP → re-flagged within seconds. The "Reconnect required" loop you're seeing. |

The dashboard cannot tell A from B. **The discriminator is the egress IP.** If
you reconnect from a residential network (your laptop at home, mobile hotspot,
home Pi/Tailscale exit), the session is "real" enough to clear. If you reconnect
from the worker's datacenter IP, it isn't.

 │   └─ YES → continue.
 │
 ├─ Q4: How long ago was the LAST hard block (automation_warning / blocked)?
 │   ├─ <48h → wait. Reconnecting too soon teaches LinkedIn the new IP is the
 │   │         same actor. Set cooldownUntil to NOW + 48h and stop syncing.
 │   └─ ≥48h → continue.

Apply this tree to every "Reconnect required" event. It replaces the
"just click reconnect again" reflex that gets accounts permanently retired.

## 4. What I shipped right now to unblock you

### 4.1 Admin clear-block endpoint
```
POST /accounts/{accountId}/clear-block
POST /accounts/{accountId}/clear-block?surface=connections
Header:  x-api-key: $API_SECRET
```
Wipes the `syncPosture` entry and the `antiBan` circuit breaker for that account
(surface or all). The next scheduled sync attempts again from scratch.

**Use only after addressing the root cause** (proxy, cooldown). Clearing without
a fix just walks back into the same wall — the endpoint's response carries that
hint explicitly.

Example:
```bash
curl -X POST -H "x-api-key: $API_SECRET" \
  http://127.0.0.1:3001/accounts/personl/clear-block?surface=connections
```

Or for the whole account:
```bash
curl -X POST -H "x-api-key: $API_SECRET" \
  http://127.0.0.1:3001/accounts/personl/clear-block
```

### 4.2 Existing primitives already in place
- `worker/src/antiBan.js::clearAccountCooldown(accountId)` — clears Redis breaker keys.
- `worker/src/syncPosture.js::clearSyncPosture(accountId)` — clears the posture hash.

The new endpoint composes them into one safe operation.

## 6. Systemic improvements (the "master plan" part)

These are the architectural changes that turn this from a recurring fire into a
managed risk. Most are sketched in earlier docs; the connections incident
clarifies which ones to prioritize.

### 6.1 Distinguish "soft expire" from "hard block" in the API surface
Right now `ERR_TOO_MANY_REDIRECTS` and `cookies stale` both render as
"Reconnect required". Add a richer posture descriptor:
```json
{
  "posture": "blocked",
  "kind": "ip_flagged",
  "egress_ip": "167.71.211.25",
  "retry_in_seconds": 172800,
  "recommended_action": "rotate_proxy"
}
```
vs.
```json
{
  "posture": "expired",
  "kind": "cookies_stale",
  "retry_in_seconds": 0,
  "recommended_action": "reconnect"
}
```
The UI then shows actionable text instead of a generic "Reconnect required".

### 6.2 Proxy required-mode by default
Flip `ANTIBAN_REQUIRE_PROXY=1` in the Nomad env once every account has a
`PROXY_FOR_<id>`. The worker then refuses to launch a browser without a proxy
URL, eliminating accidental datacenter egress that re-blocks accounts.

### 6.3 Per-account egress IP visibility
Surface the **actual egress IP** the worker sees on each sync, shown in the
dashboard. Today there is no way to confirm a proxy is engaged short of reading
worker logs. Add `egress_ip` to the per-account health endpoint by pinging
`https://api.ipify.org` through the same browser context once per sync window.
Display in the connections surface card next to the posture badge.

### 6.4 Auto-cool-down respect
"Next attempt just now" in the screenshot indicates the worker is retrying
inside the cooldown window. Audit the scheduler: `syncCadenceForPosture` (in
`SyncOrchestrator.js`) should return `Infinity` cadence when posture is `blocked`
until `nextAllowedAt` passes — otherwise we're spamming LinkedIn while waiting
for the timer, which is itself a flag.

### 6.5 Reconnect-from-residential workflow
The noVNC flow is hosted on the worker. When the user clicks "Reconnect required",
the new login happens through the **same datacenter IP**, which re-flags the
session immediately. Two architectural options:

- **Browser-side proxy detection**: refuse to start the connect flow unless a
  per-account residential proxy is configured (composes with 6.2).
- **Hybrid hosted-login**: have the user run a tiny desktop agent during connect
  (BYO-IP from `ANTI_BAN_FREE_TIER.md` §4) so the login goes through their home
  IP. The agent disconnects after cookies are captured.

The desktop-agent path is also the strategic answer to "we want something like
Unipile" — it eliminates the proxy line item and matches what Unipile actually
does internally.

### 6.6 Account quarantine policy
If an account is blocked >1 time in a rolling 30 days, auto-quarantine for 7
days and alert ops. Today blocked accounts keep cycling between blocked→
clear→blocked, which is what burns them permanently.

## 7. What this plan does NOT promise

- **Doesn't unblock LinkedIn by clearing posture alone.** The clear-block
  endpoint resets *our* state — it has zero effect on LinkedIn's view of the
  IP/account. Use it after the real fix.
- **Doesn't eliminate the need for a proxy.** Every line above assumes the
  worker eventually egresses from a non-datacenter IP. There is no software-only
  workaround for that.
- **Doesn't restore an already-burned account instantly.** Recovery from a hard
  block takes days. Plan for it.

## 8. Decision summary

| If you have… | Do this |
|---|---|
| Cooldown timer stuck, no actual ban | Call `clear-block`, retry. |
| `Reconnect required` from the datacenter IP, no proxy yet | **Do not reconnect.** Get a proxy first. Reconnecting will burn the account faster. |
| Reconnect required + a residential proxy in hand | Wire it in, `clear-block`, reconnect via noVNC from a residential network. |
| Repeated blocks within 30 days on one account | Retire the account; create a new one. |
| Pattern across multiple accounts | Your egress IP is burned. Rotate the proxy pool. |
